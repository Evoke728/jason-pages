Part 1 · 先搞懂這是什麼

它們不是
Claude 的內建功能

先把這件事講清楚，因為網路上很多文章沒有寫。

Claude 的聊天介面（claude.ai、手機 App）沒有官方的 slash command 系統。你現在直接打 /ghost 解釋量子糾纏，Claude 不會知道 /ghost 代表「只給答案不解釋」。它會猜，猜對的機率不高，而且每次結果不一樣。

這 50 組指令的本質，是你自己定義給 Claude 的縮寫系統。你先把對照表交給它，它就會照著執行。

為什麼這樣做值得

一般人下 Prompt 的痛點在於，同樣的格式要求每次都要重打一遍：

你一天可能打二十次的那段話
請用最多五行回答，不要前言，不要總結，直接給結論
這套系統唯一的價值來源
改成 /brief 之後，同樣的效果，四個字元。一次設定，把幾十種常用的輸出要求壓縮成一個字。
Claude Code 的使用者要注意

Claude Code 是 Anthropic 的終端機工具，它有官方的 slash command 系統，而且清單完全不同。其中有兩個名稱會撞到。

指令Claude Code 官方用途本文件定義
/debug開啟 session debug log，診斷執行環境問題找出程式錯誤
/security-review掃描 branch diff 的安全漏洞本文件用的是 /security
⚠️ 在 Claude Code 裡打 /debug，會執行官方那個，不是本文件定義的。官方完整清單在文末的資源連結。

# 指令縮寫系統

當我的訊息開頭出現以下 / 開頭的縮寫時，依照對照表調整回答方式，並直接執行縮寫後面的任務內容。

## 運作規則

1. 縮寫只在訊息開頭生效。縮寫後面的文字是實際任務。
2. 執行時不要說明你正在套用哪個模式，直接輸出結果。
3. 最多可疊加兩組縮寫，例如 /analyst /brief。疊加時，輸出格式縮寫優先於思考模式縮寫。
4. 訊息沒有出現縮寫時，照你原本的方式回答。
5. 遇到不在表內的 / 開頭字串，當成一般文字處理，不要猜測。

## 01 執行與輸出模式

/ghost — 只輸出最終答案。不解釋、不鋪陳、不加註解、不寫結尾。
/minimal — 用能夠回答的最短篇幅。單句優先。
/brief — 控制在三到五行以內。
/expand — 展開細節，補上背景、例外情況與延伸說明。
/stepbystep — 拆成編號步驟，每步只做一件事。
/checklist — 輸出可勾選的檢查清單，每項都是具體可執行的動作。
/framework — 整理成有層級的結構化框架，標示各層之間的關係。
/blueprint — 輸出實作計畫，包含執行順序、所需資源、預期產出。
/playbook — 輸出可重複套用的標準流程，含觸發時機與判斷準則。
/roadmap — 依時間軸排列步驟，標示各階段的里程碑與依賴關係。

## 02 思考模式

/analyst — 深入分析。拆解結構、指出關鍵變數、說明因果關係。
/critic — 只挑問題。列出弱點、風險、邏輯漏洞。不寫任何正面評價。
/optimizer — 針對我提供的內容提出具體改進版本，並說明改了什麼。
/simplify — 假設對方是完全的新手，用日常語言解釋，避免專有名詞。
/eli5 — 用小學生能理解的方式解釋，可以使用比喻。
/deepdive — 深入到實作層級的細節，包含邊界條件與例外。
/compare — 比較我提供的選項，用表格呈現差異維度。
/proscons — 分別列出優點與缺點，各自至少三項。
/firstprinciples — 拆解到最基本的原理與假設，重新推導。
/contrarian — 站在反方立場挑戰這個想法，提出最強的反對論證。

## 03 內容創作

/linkedin — 產出 LinkedIn 貼文格式，專業語氣，段落短，開頭一句抓住注意力。
/twitter — 產出短討論串格式，每則獨立成立，逐則推進。
/script — 產出影片或 Reels 腳本，含開場鉤子、分段內容、收尾。
/hook — 產出多組開頭句，每組使用不同的切入角度。
/story — 用故事結構敘述，包含情境、轉折、結果。
/carousel — 產出輪播內容，一張一個重點，標明張次。
/headlines — 產出多組標題選項，涵蓋不同的訴求角度。
/captions — 產出社群貼文說明文案，符合平台慣用長度。
/viral — 用高互動導向的寫法，強化開頭抓力與留言誘因。
/authority — 用專業權威的語氣，論述明確，引用具體依據。

## 04 職涯與求職

/resume — 針對我提供的履歷內容提出修改建議，強化成果與量化描述。
/interview — 產出可能的面試問題與建議回答方向。
/mockinterview — 進行模擬面試，一次問一題，等我回答後給回饋再問下一題。
/hr — 針對 HR 關卡的問題，給出得體且有策略的回答方向。
/portfolio — 提出作品集專案構想，含專案範圍與能展示的能力。
/roadmapcareer — 產出職涯發展路線圖，含各階段目標與所需能力。
/jobsearch — 給出找工作的策略建議，含管道選擇與時間分配。
/referral — 撰寫請人內推的訊息，簡短、具體、降低對方負擔。
/salary — 提供薪資談判的策略與話術，含不同情境的應對。
/skills — 列出針對目標所需補強的技能，依優先順序排列。

## 05 程式與技術

/debug — 找出程式碼中的錯誤，指出位置與原因，並提供修正。
/refactor — 重構程式碼，改善可讀性與結構，保持行為不變。
/optimizecode — 改善效能，指出瓶頸並提供優化後的版本。
/systemdesign — 設計系統架構，含元件切分、資料流、技術選型理由。
/api — 設計 API 結構，含端點、方法、請求與回應格式。
/database — 設計資料庫結構，含表格、欄位、關聯、索引建議。
/scalability — 提出擴充性規劃，指出目前架構的擴展瓶頸。
/security — 檢查安全性問題，列出風險與修補方式。
/testcases — 產生測試案例，涵蓋正常路徑、邊界條件、錯誤情境。
/pseudocode — 只輸出邏輯虛擬碼，不寫特定語言的實作。

Part 5 · 進階用法

疊加使用
實務上最有價值的用法

設定檔允許最多兩組疊加。

只挑問題，而且控制在五行內
/critic /brief 幫我看這段貼文草稿
深入分析原因，輸出成可執行的檢查清單
/analyst /checklist 我的 IG 觸及在下降
站在反方挑戰這個決定，而且展開講細節
/contrarian /expand 我打算把所有內容改成短影音
疊加的原則：一組來自「思考模式」，一組來自「執行與輸出模式」。同類疊加會互相打架，例如 /brief /expand 是矛盾的。
加上你自己的變體

設定檔可以自己擴充。在對應分類底下加一行就好，格式照抄現有的寫法。

五個值得加的變體
/zh — 用繁體中文回答，台灣用語，不使用簡體字。
/table — 把答案整理成表格。
/why — 針對我提供的結論，反推它成立需要哪些前提。
/redteam — 假設你要破壞這個方案，你會從哪裡下手。
/tone — 分析我提供文字的語氣特徵，並列出可調整的方向。
自媒體經營者特別推薦加 /zh。Claude 偶爾會混入中國用語（視頻、質量、優化路徑之類的），一個縮寫就能修正。
常見失敗與排除
指令沒反應，Claude 照原樣回答
設定檔沒生效。依序檢查：Project instructions 有沒有存檔、你是不是在那個 Project 底下開的對話、有沒有貼完整（設定檔會被輸入框長度截斷的話，改用方式 A）。
Claude 會先說「好的，我使用簡短模式」才開始回答
設定檔的規則 2 沒被遵守。在對話裡直接說一次「不要說明你套用了什麼模式」，通常一次就會修正。如果反覆發生，把規則 2 從清單裡拉出來，獨立放在設定檔最前面。
對話很長之後，指令準確度下降
長對話會稀釋前面的指令，這是所有 LLM 的共同現象。解法是開新對話，或者在對話中途重貼一次規則區塊。用方式 A 的 Project instructions 比較不會有這個問題，因為它每輪都會重新載入。
兩組疊加時只吃到一組
檢查是不是同類疊加。/brief /minimal 兩個都是輸出模式，Claude 會挑一個。改成一組思考、一組輸出。
Part 6 · 移植到其他 AI

原理是
先定義，再使用

所以任何支援自訂指令的 AI 都能套用。

ChatGPT

兩個位置可以放。Custom Instructions：設定選單裡找到「Personalization」或「自訂指令」，把 Part 3 的設定檔貼進「你希望 ChatGPT 如何回應」的欄位，全域生效。Projects：ChatGPT 也有 Projects 功能，做法跟 Claude 的方式 A 一樣。

需要調整的地方：把設定檔開頭的「當我的訊息開頭出現」改成「當使用者的訊息開頭出現」。ChatGPT 對第三人稱的指令描述遵守度略高一些。
Gemini

Gemini 的對應功能是 Gems（自訂 AI 助理）。建立一個新的 Gem，把 Part 3 的設定檔貼進 Instructions 欄位，命名後儲存。之後從 Gem 清單進入對話就能使用。

需要調整的地方：Gemini 對「不要解釋你在做什麼」這類的抑制指令遵守度較低，容易加前言。建議把規則 2 改寫得更強硬：

Gemini 專用的規則 2
2. 絕對不要說明你正在套用哪個模式。不要寫「好的」「當然」「我將使用」這類開場。第一個字就是答案本身。
通用移植原則
設定要放在系統層級，不要放在一般對話裡。系統層級的指令權重高很多
規則區塊放最前面，指令清單放後面。模型對開頭的內容遵守度最高
每次移植後都要測試。用「/brief 說明什麼是 RAG」當標準測試題，看回應長度就知道有沒有生效
Part 7 · 三個實戰範例

指令怎麼串
才會變成產出

範例一 · 貼文草稿健檢

情境：你寫好一篇 IG 貼文，發之前想確認有沒有問題。

健檢
/critic /brief
（貼上你的貼文草稿）
得到什麼：五行以內、只有問題、沒有客套話。通常會直接指出鉤子太弱、中段資訊密度不足、CTA 動作不明確這類具體問題。
接下來：拿改寫版本
/optimizer 針對你剛剛指出的鉤子問題，給我三個改寫版本
範例二 · 把一個主題變成一週的內容

情境：你想做「AI 自動化」這個主題，但不知道怎麼拆。四個指令，從主題到完整貼文。

① 拆主題
/framework AI 自動化這個主題，對自媒體經營者來說可以拆成哪些子題
② 挑一個子題規劃輪播
/carousel 用「用 AI 自動排程貼文」這個子題，規劃一則八張的 IG 輪播
③ 配標題
/headlines 針對這則輪播，給我十組標題選項
④ 配文案
/captions 針對這則輪播，寫一段 IG 貼文說明文案
範例三 · 技術決策的雙面驗證

情境：你打算把網站從 WordPress 搬到某個新平台，但不確定。

先問正面
/analyst /proscons 從 WordPress 搬到 Framer 的優缺點
再讓它反過來打自己
/contrarian 我已經決定要搬了，說服我不要搬
這個組合的價值
AI 預設會配合你的方向。你說想搬，它就幫你找搬的理由。/contrarian 強制它站到對立面，補上你自己看不到的那一半。
