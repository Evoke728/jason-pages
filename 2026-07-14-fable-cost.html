03 · 核心心法

Fable 貴在「想」
不貴在「寫」

如果你只記得這份文件的一句話，記這句：

核心
Fable 5 的價值在「想」，不在「寫」。把「想」留給 Fable，把「做」交出去。

Anthropic 官方的說法是：Fable 是「見過幾乎沒人見過的問題的專家」。它的價值在長鏈條、多步驟、複雜的判斷——那種你卡了三天、換了三個方法都不行的問題。

而你 90% 的時間，其實是在做這些事：讀檔案、改變數名稱、跑測試、寫 boilerplate、查文件、把 A 格式轉成 B 格式。這些事 Sonnet 5 做得跟 Fable 5 一樣好，價格是五分之一。用 Fable 5 做這些，等於用兩倍的錢買 Sonnet 做得到的事。

04 · 五個招式

把工作
分給對的模型

招 01把 effort 調下來

/effort 是 Claude Code 的官方指令，控制模型回應前要花多少 token 去「想」。它同時決定模型會讀多少檔案、跑多少指令、驗證幾次、回應多長。五個檔位由少到多：low → medium → high → xhigh → max。Fable 5 的預設是 high。

官方說：Fable 5 在較低的 effort 設定下表現依然很好，經常還超過前代模型在 xhigh 的表現。翻成人話——你把它降到 medium，可能還是比開到最大的舊模型強，那你為什麼要付 high 的錢。
在 Claude Code 裡
# 開啟互動式選單
/effort

# 或直接設定
/effort medium
/effort low
/effort high

# 回到模型預設值
/effort auto
啟動時指定
claude --effort medium
環境變數（優先權最高）
export CLAUDE_CODE_EFFORT_LEVEL=medium
什麼時候用哪一檔
檔位適合的任務
low改變數名稱、修 typo、產 boilerplate、「這個函式回傳什麼」、跑輕量 subagent
medium範圍明確的修改、單檔案的功能新增、一般日常開發
high真正的開發工作、跨檔案的邏輯
xhigh難的多步驟問題、大型重構
maxhigh / xhigh 已經失敗過的問題、架構決策、安全審查
⚠️ 兩個坑：① low 不適合需要「看全局」的任務——有人用 low 跑重構，Claude 直接把函式改名沒查誰在呼叫，三個 import 壞掉。② 中途換檔會讓 prompt cache 失效，下一輪用全價重讀整段對話。要換，在開新 session 時換。
持久性：low / medium / high / xhigh 會跨 session 保留；max 只在當前 session 有效，結束就重置。
招 02讓它當架構師，不當工人

Claude Code 的 plan mode：讓模型先把整件事想清楚、寫成計畫，但不動手。流程變成——Fable 5（plan mode）產出一份規格書 → Sonnet 5 / Opus 4.8 照著執行。Fable 5 的 token 只花在「想架構」，剩下讀檔、寫檔、跑測試、debug 全由便宜的模型完成。

為什麼有效：一個開發任務的 token，規劃架構約 5%、讀檔寫碼跑測試修 bug 約 95%。全程用 Fable 5，那 95% 都是用兩倍價買 Sonnet 做得到的事。把 95% 移走，成本從 $10/$50 降到 $2/$10。
第一步 · 讓 Fable 5 產出規格書
你現在是架構師，不是工程師。

進入 plan mode。

任務：[在這裡描述你要做的事]

我要你做的：
1. 讀完相關的程式碼，理解現有結構
2. 設計完整的實作方案
3. 把方案寫成一份 markdown 規格書，存成 SPEC.md

規格書必須包含：

- 新增的函式 / 元件的簽名與職責
- 資料流：輸入 → 處理 → 輸出
- 邊界情況與錯誤處理
- 測試要驗證哪些行為
- 執行順序（哪一步必須在哪一步之前）

規格書要寫到「一個不熟悉這個 codebase 的工程師，
照著做就能完成」的程度。

你不要寫任何實作程式碼。
第二步 · 換模型，交給便宜的執行
/model sonnet

讀 SPEC.md，照著執行。

規則：
- 完全按照規格書執行，不要自己加功能
- 遇到規格書沒寫到的情況，先停下來問我，不要自己決定
- 每完成一個檔案，跑一次相關測試
- 完成後回報：改了哪些檔案、測試結果
什麼時候用：跨多檔案的功能開發、重構、從零開始的新模組、任何你自己都還沒想清楚怎麼做的任務。什麼時候別用：單行修改、改文字、修 typo——直接用 Sonnet 或 Haiku，連 plan 都不用。
招 03讓它少寫一點

輸出 token 比輸入 token 貴 5 倍（所有 Claude 模型都是 1:5）。所以砍成本最有效的地方，是砍掉模型「寫出來」的東西。有兩個 open source 的 skill 專門在做這件事。

Ponytail｜把「懶惰的資深工程師」裝進 AI

作者 DietrichGebert。它讓 AI 寫任何程式碼之前，先爬一個決策階梯，停在第一個成立的那一階：

  • 這東西有必要存在嗎？→ 沒有，跳過（YAGNI）
  • codebase 裡已經有了嗎？→ 有，直接用，別重寫
  • 標準函式庫做得到嗎？→ 用標準函式庫
  • 平台原生功能做得到嗎？→ 用原生功能
  • 已安裝的套件做得到嗎？→ 用它
  • 一行寫得完嗎？→ 一行
  • 以上都不行 → 才寫，而且只寫最小可行版本
指標作者實測結果
程式碼行數少約 54%（過度設計情境最高到 94%）
成本降約 20%
速度快約 27%
安全性100% 通過對抗測試（path traversal、SQLi、token 偽造等）

最經典的例子：叫 AI 做一個倒數計時器，沒裝的版本蓋了 190 行、附帶沒人要求的動畫「儀表板」。Ponytail 版本：13 行。它明確保留了信任邊界驗證、資料遺失處理、安全性、無障礙——是「懶，但不失職」。

安裝 Ponytail（強度分級 lite / full / ultra）
claude plugin marketplace add DietrichGebert/ponytail
claude plugin install ponytail@ponytail
Caveman｜砍掉所有客套跟廢話

作者 JuliusBrussee。讓 AI 用「原始人語法」講話，砍掉所有廢話。程式碼、指令、錯誤訊息完全不動。「我已經成功完成了認證模組的重構，Token 驗證現在能處理邊界情況…」→「Auth 模組重構完成。Token 驗證處理邊界情況。加了錯誤處理。向後相容。」

安裝 Caveman（/caveman lite / full / ultra）
claude plugin marketplace add JuliusBrussee/caveman
claude plugin install caveman@caveman
⚠️ 誠實的期待值管理：網路上說「Caveman 省 65%」——那只適用於「說明文字」那一小塊。一場 100,000 token 的 session，說明文字大概只佔 6,000。壓縮 65% 省下約 4,000，整場實際只省 4–5%，不是 65%。還是推薦裝（免費、終端機乾淨、能壓縮 CLAUDE.md），但別指望它救帳單。真正砍成本的是招 02、04、05 的「換模型」；Ponytail 的 20% 才是實打實，因為它砍的是貴 5 倍的輸出程式碼。
招 04查資料交給便宜的模型

/deep-research 是 Claude Code 內建的第一方 workflow（不是第三方外掛）。你丟一個問題，它會：先問你 2–3 個釐清問題 → 在背景撒出大量 subagent 平行搜尋、抓取來源 → 讓不同 agent 互相對抗性驗證 → 合成一份帶引用的報告。

關鍵：整個過程在背景跑，你的 session 保持可用。中間所有搜尋、抓取、驗證的 token 都留在 workflow 腳本裡，不塞進主對話——Claude 的 context 只拿到最後那份報告。

查資料是體力活不是腦力活，Sonnet 5 做得完全夠；而 deep research 會大量燒 token，這正是你最不想用 $10/$50 的地方。

第一步 · 切到便宜的模型
/model sonnet
第二步 · 跑 deep research
/deep-research

我要研究 [主題]。

範圍：
- 時間範圍：[例如：2026 年之後的資料]
- 來源類型：[例如：官方文件、原始論文、公司部落格，
  排除內容農場]
- 我要回答的核心問題：[列 2-3 個]

輸出：
- 一份 markdown 報告，存成 RESEARCH.md
- 每個主張都要有來源連結
- 明確標出哪些地方各家說法互相衝突
- 明確標出哪些地方資料不足
第三步 · 報告交給 Fable 5，只讓它做判斷
/model fable

讀 RESEARCH.md。

不要重新查資料，不要驗證來源，那些已經做完了。

我只要你做一件事：根據這份報告，做出架構判斷。

回答：
1. 這幾個方案，你建議選哪一個？為什麼？
2. 這個選擇最大的風險是什麼？
3. 報告裡有哪個地方你認為結論下錯了？
這一招的精髓
用便宜的模型建立 context，用貴的模型做決策。Context 建立是 token 密集、智力不密集；決策是 token 稀疏、智力密集。分開，錢就省下來了。
招 05讓 Fable 5 只當顧問

/advisor 讓你把「主模型」跟「顧問模型」拆開。主模型（執行者）是便宜的模型，每一輪都在跑，負責讀檔、寫檔、跑指令；顧問模型是貴的模型，只在關鍵時刻被叫進來。顧問會拿到完整對話歷史（含每次工具呼叫與結果），回傳一段指引。顧問什麼都不能碰——不能讀檔、跑 shell、上網，只能讀對話給建議，這是硬性的架構邊界。

設定：Sonnet 執行 + Fable 顧問
# 設定主模型為 Sonnet
/model sonnet

# 設定 Fable 5 為顧問
/advisor fable

# 或用選單
/advisor
寫進設定檔 settings.json
{
  "model": "sonnet",
  "advisorModel": "claude-fable-5"
}
⚠️ 很多人踩到的官方限制：顧問模型必須比主模型更強，否則不會啟用。Sonnet+Fable ✅、Haiku+Fable ✅、Opus+Fable ✅；但 Fable+Opus ❌（顧問比主模型弱）、Sonnet+Sonnet ❌。想省錢就是 Sonnet 執行 + Fable 顧問。

你不能手動叫顧問。顧問是主模型自己決定要不要叫的。Claude 通常在這些時候叫：準備鎖定一個做法之前、同一個錯誤重複卡住、準備宣告任務完成之前。想讓它叫對時機，把規則寫進 CLAUDE.md：

貼進 CLAUDE.md
## Advisor 使用規則

- 開始實作之前，先諮詢 advisor 確認策略與設計
- 跨多個檔案的改動，動手前一定要問 advisor
- 同一個錯誤出現兩次以上，去問 advisor，不要自己一直試
- 宣告任務完成之前，問一次 advisor
- 長任務至少呼叫兩次：鎖定做法前一次，宣告完成前一次
計費：每次顧問呼叫都把對話送給顧問模型，按顧問費率計費，疊加在主模型用量之上——所以次數要控制，這也是為什麼要在 CLAUDE.md 寫清楚「什麼時候該叫」。
⚠️ 已知問題：/advisor 目前標記為實驗性，需要 Claude Code v2.1.98 以上；用 Fable 5 當顧問需要 v2.1.170 以上。不支援 Amazon Bedrock、Google Cloud Agent Platform、Microsoft Foundry。遇到怪錯誤先升級 Claude Code。

05 · 三個官方成本槓桿

大部分人
沒開的三個開關

上面五招是「怎麼分配工作」。這三個是「怎麼付更少錢做同一件事」——都是 Anthropic 官方功能，不是外掛。

槓桿 1｜Prompt Caching（省最多，最少人開）

快取命中的輸入 token，只要付原價的 10%。省 90%。

模型標準輸入快取命中
Fable 5$10$1
Opus 4.8$5$0.50
Sonnet 5（優惠）$2$0.20

把重複使用的內容（system prompt、工具定義、文件、CLAUDE.md）標記起來。第一次寫入快取成本是標準輸入的 1.25 倍（5 分鐘 TTL）或 2 倍（1 小時 TTL），之後每次讀取只要 10%——第一次重用之後就開始賺錢。你能做得更好的：CLAUDE.md 保持精簡、任務之間 /clear、別在 session 中途換模型或 effort（會讓 cache key 失效全價重讀）。

槓桿 2｜Batch API（非即時工作，直接對折）

輸入輸出全部 5 折，24 小時內非同步處理完。適合夜間自動化、大量文件處理、評測、內容批次生成。可以跟 prompt caching 疊加——「有快取 + 走 batch」的請求，成本可以低到標準價的 5%。

槓桿 3｜模型路由（最直接的一招）
模型價格（輸入/輸出）拿來做
Haiku 4.5$1 / $5分類、抽取、路由、摘要
Sonnet 5$2 / $10生產環境預設值
Opus 4.8$5 / $25複雜推理、agentic 開發
Fable 5$10 / $50長鏈條、卡死你的問題

Fable 5 的輸出 token 是 Haiku 4.5 的 10 倍價。原則：從最便宜的開始，有證據才往上升級。不要因為「反正 Fable 最強」就一路 Fable——你付的是 10 倍價，換來的可能是同一個答案。

07 · 五個常見錯誤

別踩
這五個雷

  • 錯誤 1｜整場 session 都掛在 Fable 5 上——90% 的 token 花在 Fable 做 Sonnet 做得到的事。最貴、也最容易犯。
  • 錯誤 2｜在 session 中途換模型或換 effort——cache key 失效，下一輪全價重讀整段對話。要換，開新 session。
  • 錯誤 3｜把 effort 設在 low 去跑重構——低 effort 只做「最少的事」，會直接改名，然後三個 import 壞掉。
  • 錯誤 4｜以為 Caveman 能省 65%——它只壓縮那 6% 的說明文字，整場實際省 4–5%。裝它，但別靠它。
  • 錯誤 5｜CLAUDE.md 寫成一部小說——它每一輪都在 context 裡，臃腫的 CLAUDE.md 就是一筆每輪都在付的稅。
